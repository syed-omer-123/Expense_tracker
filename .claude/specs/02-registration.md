# Spec: Registration

## Overview

Step 2 turns the existing static registration page into a working sign-up flow. Today `GET /register` only renders `register.html`, and the form posts to a URL that has no handler. This step adds the `POST /register` handler that validates the submitted name, email and password, stores a new user with a hashed password, and sends the visitor on to the login page. It is the first feature that writes user data through the database layer built in Step 1, and it gives Step 3 (login/logout) real accounts to authenticate against. Registration does not log the user in; sessions belong to Step 3.

## Depends on

- Step 1 — Database setup (`users` table, `get_db()`, `init_db()`). Already complete.

## Routes

- `GET /register` — render the registration form (existing, unchanged behaviour) — public
- `POST /register` — validate the form, create the user, redirect to `/login` on success, or re-render the form with an error on failure — public

`GET /register` and `POST /register` are handled by the same `register()` view, using `methods=["GET", "POST"]`.

## Database changes

No database changes. The `users` table in `database/db.py` already has `id`, `name`, `email` (UNIQUE, NOT NULL), `password_hash` and `created_at`.

New helper functions are added to `database/db.py` (no schema change):

- `create_user(name, email, password)` — hashes the password with `generate_password_hash`, inserts the row with a parameterised query, commits, and returns the new user id. Lets `sqlite3.IntegrityError` propagate on a duplicate email so the caller can handle it.
- `get_user_by_email(email)` — returns the matching `sqlite3.Row` or `None`. Used for the duplicate-email pre-check and reusable by Step 3.

## Rules for implementation

- No SQLAlchemy or ORMs
- Parameterised queries only — never f-strings or `%` formatting in SQL
- Passwords hashed with werkzeug (`generate_password_hash`); never store or log the plain-text password
- Use CSS variables — never hardcode hex values (any new CSS must use the variables defined in `static/css/style.css`; prefer reusing `.auth-error`, `.form-input`, `.btn-submit`)
- All templates extend `base.html`
- All DB logic lives in `database/db.py`; the route only reads the form, calls helpers, and renders or redirects
- Use `url_for()` for every internal link and redirect — no hardcoded URLs
- Use `abort()` for HTTP errors rather than returning bare strings
- Do not implement any stub route (`/logout`, `/profile`, `/expenses/...`) and do not add sessions, `secret_key` or auto-login; those belong to later steps
- Server-side validation (the browser's `required` / `minlength` is not enough):
  - `name`: trimmed, must not be empty
  - `email`: trimmed and lower-cased before storing and before the duplicate check; must not be empty and must contain a single `@` with text on both sides
  - `password`: at least 8 characters
  - Duplicate email → error message "An account with that email already exists." Catch `sqlite3.IntegrityError` as well, so a race between the pre-check and the insert cannot cause a 500
- Failed validation re-renders `register.html` with the `error` message and HTTP status 400 (409 is acceptable for the duplicate email case)
- Successful registration returns `redirect(url_for("login"))`
- Do not change the port (5001) or the existing `landing`, `login`, `terms` and `privacy` routes

## Definition of done

- [ ] `python app.py` starts on port 5001 without errors
- [ ] Visiting `/register` still shows the form, and the form's action is generated by `url_for` (no hardcoded `/register` in the template)
- [ ] Submitting a valid name, new email and an 8+ character password redirects to `/login`
- [ ] The new user appears in the `users` table with the name as entered, the email lower-cased, and a `password_hash` that is not the plain-text password (starts with a werkzeug hash prefix such as `scrypt:` or `pbkdf2:`)
- [ ] `check_password_hash` on the stored hash succeeds for the submitted password
- [ ] Registering again with the same email (including with different letter casing, e.g. `A@X.com` vs `a@x.com`) shows "An account with that email already exists." and creates no second row
- [ ] A password shorter than 8 characters shows an error and creates no user
- [ ] An empty or whitespace-only name shows an error and creates no user
- [ ] An email without `@` (submitted directly, bypassing browser validation) shows an error and creates no user
- [ ] After any failed submit, the name and email fields keep the entered values and the password field is empty
- [ ] Error responses have HTTP status 400 (or 409 for duplicate email), not 200 or 500
- [ ] The seeded demo user (`demo@spendly.com`) is unaffected and registering with that email is rejected as a duplicate
- [ ] No SQL in `app.py`; all queries in `database/db.py` use `?` placeholders
- [ ] `pytest tests/test_registration.py` passes
